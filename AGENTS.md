# AGENTS.md

This file provides guidance to AI coding agents working with code in this repository.

## Project

Ultimate Siegery is a Next.js app for Rainbow Six Siege players.
It lets users build and save operator loadouts, generate random loadouts, and browse in-game challenges.
Stack: Next.js 16 (App Router, React 19), shadcn/ui on Tailwind v4, Supabase Postgres accessed through Drizzle ORM, Clerk for auth, pnpm.

## Commands

```bash
pnpm dev                    # Next dev server
pnpm build                  # Production build
pnpm lint                   # ESLint (next core-web-vitals + prettier)
pnpm exec tsc --noEmit      # Type check
pnpm format                 # Prettier write
pnpm format:check           # Prettier check

supabase start              # Local Supabase via Docker (needs Docker running)
supabase status             # Print local URLs/keys for .env.local
supabase db reset           # Reapply supabase/migrations and then supabase/seeds/*.sql
```

There is no test suite.
CI (`.github/workflows/`) runs lint, type check, build, and `format:check` on PRs to `main`, so run all four before considering a change done.

Env vars live in `.env.local` (template in `.env.template`).
`next.config.mjs` throws if `NEXT_PUBLIC_SUPABASE_URL` is unset, so even `pnpm build` needs it; CI uses placeholder values.

## Architecture

### Request flow and layering

Data access goes through three layers, and new features should follow the same shape:

1. **Services** (`src/lib/services/*.ts`) do the real work.
   Each one calls Clerk's `currentUser()`, queries Drizzle, and returns a discriminated result built with `ok(statusCode, data)` / `err({ statusCode, ... })` from `src/lib/errors.ts`.
   Services never throw; they catch and return `INTERNAL_SERVER_ERROR`.
2. **Server actions** (`src/lib/api/<entity>/queries.ts` and `mutations.ts`, marked `"use server"`) wrap services.
   They switch exhaustively on `response.error.statusCode` (with `satisfies never` in the default branch), `redirect("/")` on `UNAUTHORIZED`, and call `revalidatePath` after successful mutations.
   If a service gains a new error status code, every action switch over it must handle that code or the type check fails.
3. **Pages** under `src/app/(authorized)/` are async server components with `export const dynamic = "force-dynamic"`.
   They call a query action, throw on error (caught by `src/app/error.tsx`), and pass data to a client component in `src/components/view/`.
   Client components call mutation actions directly.

The only route handler is `src/app/api/operators/[id]/route.ts`, fetched with SWR from `EditLoadoutDialog`.
It duplicates the operator reshaping logic in `services/operator.ts`, so changes to the operator response shape must be made in both places.

Services reshape Drizzle's nested relation results (`op_weapons`, `operator_gadgets`, `loadout_weapon_attachments`) into the camelCase shapes in `src/lib/types/types.ts` (`OperatorFullLoadout`, `LoadoutDisplay`, attachments keyed by lowercase type).
DB columns stay snake_case; app-facing types are camelCase.

### Auth

Clerk route protection is in `src/proxy.ts` (Next 16's replacement for `middleware.ts`).
Its `isPrivateRoute` matcher is built from `privateRoutes` in `src/lib/site.ts`, which must be kept in sync with the route folders under `src/app/(authorized)/`.
`src/app/robots.ts` disallows the same list.
Services additionally scope every loadout query and mutation by the Clerk `user.id` stored in `loadout.user_id`; this is the actual per-user authorization, since the app connects to Postgres directly rather than through Supabase's RLS-enforced client.

### Database

- `supabase/migrations/` is the source of truth for schema, and `supabase/seeds/` holds the static game data (operators, weapons, attachments, gadgets, and their join tables).
- `src/lib/db/schema.ts` and `relations.ts` were generated by `drizzle-kit pull` (introspection, config in `drizzle.config.ts`).
  The generated `src/lib/db/0000_*.sql` is commented out on purpose and is not used to migrate.
  Schema changes go in a new Supabase migration first, then the Drizzle schema is regenerated or updated to match.
- `src/lib/db/index.ts` creates the Drizzle client over `postgres-js` using `DATABASE_URL`, loading `.env.local` itself via dotenv.
- Operator/weapon images are served from Supabase storage; `next.config.mjs` allowlists the Supabase host for `next/image`.

### UI

- `src/components/ui/` is shadcn/ui (new-york style).
  Note `components.json` points `css` at `src/app/globals.css`, but the real stylesheet is `src/styles/globals.css`.
- `src/components/view/` holds the client-side page bodies; `custom/` holds loadout-building selects, `dialogs/` the edit/delete loadout dialogs, and `general/` shared layout pieces.
- Challenges are static data in `src/lib/data/challenges.ts`, not stored in the database.
- Legal pages (`src/app/(legal)/`) are MDX, styled through `mdx-components.tsx`.

## Conventions

- Import alias `@/*` maps to `src/*`.
- Prettier uses `objectWrap: "collapse"`, so short objects are reformatted onto one line; let `pnpm format` handle layout.
- ESLint warns on `console.log`; only `console.warn` and `console.error` are allowed.
- Generated files that should not be hand-edited: `src/lib/db/meta/`, `pnpm-lock.yaml`.
